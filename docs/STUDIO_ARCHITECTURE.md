# Pandora Saga Build Studio — карта модулей и зависимостей

## Граница данных и кода

**Игровые идентификаторы, баланс и исходные JSON актуального игрового сервера сохраняют постоянные пути** `data/os/*.json`, независимо от названий модулей интерфейса. Нельзя переименовывать ID классов, умений, предметов или пространств D1 ради «красоты» репозитория: они используются в билдах, ссылках, сохранениях и игровой энциклопедии.

## Географическая модель: город Астир и три независимых государства

Идентификаторы из официального `/gamedata/trades.json` — `1002001` (Союз северных племен Ванриг), `1003001` (Королевство Сэнт-Фальстайн), `1004001` (Лотарская империя) — используются для данных государств и NPC обменов. Нельзя переносить NPC из этих записей в районы Астира по сходству названий.

В Астире есть Центральная площадь (`1001004`) и три отдельных района (`astir-union`, `astir-empire`, `astir-kingdom`). Эти три строковых ID — только ссылки энциклопедии, НЕ серверные ID; в D1 и исходные JSON не записываются. Маршрутов в энциклопедии нет.

**Единственный NPC города с подтверждением в предоставленном игровом клиенте:** Кларис, мастер открытия сундуков, расположена на Территории Королевства города Астир (`astir-kingdom`). Профиль `astir-npc-kingdom-claris` не выдаётся за числовой ID сервера. Координаты не подтверждены, поэтому отсутствуют. Неправильное имя «Культье», неверная Территория Империи и все старые списки предполагаемых NPC из устаревшей японской вики удалены с активного сайта.

Публичный `https://pandorasaga-os.com/gamedata/trades.json` содержит только NPC обменов. Пока актуальный полный реестр NPC игрового клиента не доступен, **Территория Союза и Территория Империи не показывают придуманные записи**. Поиск, карточка, переходы и возврат по URL работают для подтверждённых NPC, а физические источники в D1 не меняются. Проверки: `tests/astir-nations-separation.test.mjs` и браузерный Chromium.

## Редактируемые специальные справочники D1 (0.322)

В админском режиме новые записи Астира сохраняются в **существующей** Cloudflare D1 таблице `overrides` через `POST /api/admin/override`: `wikiedit.map.astir-{union|empire|kingdom}`, `wikiedit.npc.astir-npc-{union|empire|kingdom}-<slug>`. Это отдельные ручные слои поверх базовых игровых данных, **не новые серверные OS ID**. Авторизованный Worker валидирует имена RU/EN, описания, координаты, услуги и массив карт (одна из трёх территорий или центральная площадь).

`PandoraWikiOwnerData.apply` собирает `townMaps` и `townNpcs`, затем `PandoraWikiData.build` строит индексы поиска, NPC → локации и локация → NPC из одной эффективной модели. Редактор изменения имени/описания использует общий механизм сохранения по потере фокуса; карточка NPC позволяет изменить территорию, а карточка района — добавить новый NPC с подтверждёнными администратором RU/EN именами. Переопределения доступны в «Все правки» и экспорте PR.

**Деплой:** публикация GitHub Pages не обновляет Worker. Перед обещанием работающего D1-редактора необходимо подтвердить `GET /api/runtime-capabilities` с `virtual-town-wiki` и `bilingual-wiki`. Worker и D1 текущей среды нельзя считать обновлёнными только на основании CI.

## Жизненный цикл обновления игрового каталога

1. Администратор нажимает **Проверить обновления игрового каталога**. Только авторизованный Worker запрашивает 17 разрешённых JSON с оригинального сервера. Клиент не загружает чужой серверный API во время обычной игры.
2. Проверяются `meta.counts` и полнота локализации. 19 пространств D1 имеют стабильные имена. Старый активный снимок не меняется.
3. Данные D1 считываются с одним `X-PS-Catalog-Snapshot`; другие версии в одном сравнении запрещены.
4. Администратор видит все отличия, включая **метаданные сервера**, и выбирает что принять. Новые изменения по умолчанию не выбраны.
5. `compose()` создаёт новый снимок без изменения исходных объектов, пересчитывает `counts` и `localeCounts`. Если результат не соответствует оригинальному полному снимку OS, его официальный `sha` удаляется и добавляется `curated`.
6. `normalize()` проверяет состав всего набора; `worker/index.js` загружает новые записи в отдельный `snapshot`, проверяет количество и переключает активный указатель только по `expectedActive`. При конфликте возвращает 409.
7. При публикации нового снимка **Legacy-переводы из текущей D1 сохраняются дословно с их оригинальными ключами и метаданными источника**. Игровая сверка не изменяет переводы из локального архива без отдельного подтверждения.
8. Обновление **файлов GitHub — отдельное действие**: выгрузить `pandora-studio-reviewed-catalog.json`, проверить `npm run catalog:review -- FILE`, затем `--write`, Git diff, тесты и PR. Не хранить GitHub PAT на сайте. Старые клиентские билды не переписываются.

## Проверки перед любым рефакторингом или обновлением OS

```bash
node scripts/audit-studio-dependencies.mjs
npm test
npm run release:check
npm run test:browser
```

Аудитор проверяет реальные HTML-файлы, наличие скриптов/стилей, отсутствие старых названий и порядок критичных модулей; Node проверяет расчёты, права, модель D1, сохранение, выборочную синхронизацию; Chromium проверяет игровой интерфейс и админский сценарий.

**Граница достоверности:** даже все зелёные тесты не доказывают точное совпадение HP/MP, итоговой защиты, магического усиления и игрового клиента OS. Серверные исходные JSON подтверждают данные, но не весь порядок внутренних расчётов; это отдельный реестр в `docs/OS_LIVE_PARITY_CHECKS.md`.

## Прямая публикация через GitHub PR

Скрипт `worker/pandora-studio-github-catalog-pr.js` принимает только опубликованный снимок D1, идентифицированный `snapshot` и проверенный повторно. Он всегда обращается к одному репозиторию и `bonaqu_projects`; клиент не может указать внешний URL или путь к секретным файлам. Контент ограничен 17 игровыми JSON в `data/os/`. Авторизация администратора защищает endpoint, а GitHub-файн-грейнд токен хранится исключительно как Cloudflare Secret.

Отдельная административная проверка D1 использует временную строку `catalog_entries` и удаляет её перед подтверждением. Проверка не переключает `catalog_current` и не подтверждает совпадение формул с игровым сервером. Это испытание записи, а не игровой публикации.



## 0.329.0 — безопасная привязка расовых навыков к текущей расе

`PandoraGameNavigation.canonicalRacialPassiveId(catalog, raceIndex, savedId)` — единый канонический источник проверки расовой пассивки. Преобразует допустимые старые строковые ID в числа только после проверки принадлежности текущей расе по `racialPassives.json`; неизвестные, испорченные, чужие и неподгруженные навыки превращаются в `null`.

`previewBaseStats()` передаёт в `PandoraOSCalculator.base()` именно канонический ID, поэтому расовые эффекты не могут начисляться до UI-сброса некорректного сохранённого значения. Визуальный редактор продолжает очищать такое состояние при отрисовке, но математическая корректность больше не зависит от порядка рендеринга. Другие атрибуты и билд-поля не меняются. Тесты: `tests/racial-passive-ownership.test.mjs`.

## 0.334.0 — канонический путь к эффектам и защита импортированного билда

Центральная функция `PandoraOSCalculator.sourceEffects` проверяет границы заточки `0..10`, числовой ID исходного `item:<id>` или `soul:<id>` относительно самого каталожного объекта, отсутствие испорченных/null строк эффекта. Подставленный source ID другого предмета не может получить ни базовые, ни структурированные Forth-эффекты; синтетические текстовые ID fixture по-прежнему допустимы в изолированных тестах, но никогда не наследуют чужую запись `itemForth[id][grade]`.

`gatherEffects` обрабатывает только конечные числа `effect.a` без `Number(null)`, `Number(true)` или строкового принудительного преобразования. Словари типов эффектов используют `Object.hasOwn`, поэтому унаследованные имена вроде `toString` и `__proto__` не выдаются за разрешённые игровые функции. Это общее исправление для ОЗ, ОМ, базовых атрибутов и сопротивлений; серверные коэффициенты не изменены. Тест `tests/structured-effect-source-identity.test.mjs` сохраняет реальный эталон эльфа-воина 149/44 и кольцо 155/44. Локальные черновики и облачные билды не перезаписываются при пересчёте.

## 0.335.0 — единые переводы книги и безопасная классификация расходников

Словари `bookLineHeads` и `bookLineFragments` остаются едиными источниками RU/EN текстов. Их упорядоченные массивы пар вычисляются при инициализации модуля один раз, чтобы не создавать повторно на каждом `bookText()` во время перерисовки сотен узлов. Проверки фиксируют перевод допустимых числовых подписей и запрет случайного перевода пользовательского имени, начинающегося с «ОЗ: ».

Только два источниково проверенных расходника `EP_DESTINED_POISON` (50022/50056) выводятся как опасные в разделе эффектов, а не как лечение. Не складывать неизвестное `a=50` с ОЗ/ОМ или манипулировать этим числом как шансом срабатывания. Клик открывает исходную карточку игровой энциклопедии; D1 и наборы предметов не меняются.

## Защита полноты расовых пассивок (0.413.0)

Поле `meta.counts.racialPassives` проверяется вместе с `skills` в `PandoraWikiCatalog.validate`; источник пассивок не может быть урезан при публикации без обнаружения ошибки. Внутри расового реестра проверяются непротиворечивые `raceId`, `key` и уникальность навыков между расами, помимо уже имеющихся проверок `skillType=PASSIVE` и `branch=race`. Всё делается до рендера энциклопедии; ошибки в D1 **не исправляются подменой на архивный список** в строгом рабочем режиме.

## Общая проверка расового реестра для Энциклопедии и героя (0.414.0)

Функция `PandoraWikiCatalog.validateRacialPassives(racialPassives,skills,counts)` используется дважды: при полной загрузке Энциклопедии и **до** установки активного `catalogSource` в редакторе героя. Оба пути отвергают неполный D1 реестр, повторное назначение пассивки другой расе и неверный `PASSIVE/race` тип. Валидация происходит до расчётов, не требует отдельного API и не подменяет списки рас в памяти или сохранениях. Обновление каталога OS остаётся явным процессом владельца.

## Порядок фиксации правок D1 и обновления карточек (0.415.0)

Сохранение мест появления, добычи, сундуков, обменов NPC и ручных источников предмета ожидает завершения `refreshOwnerCatalog()`, прежде чем снимается индикатор сохранения. Запрос `/api/admin/override` или `/api/admin/reset` выполняется первым, затем обновляются локальные правки и обратные индексы Энциклопедии. Операции не запускают «забытый» Promise, который может поменять раздел уже после сообщения об окончании. Это **не атомарная транзакция сразу нескольких ключей D1** и не подтверждение production write-теста: такой тест требует отдельной авторизованной сессии владельца. Отдельный `tests/wiki-owner-write-lifecycle.test.mjs` проверяет задержанное обновление без подключения к Cloudflare.

## Замена исходного места появления одной записью (0.416.0)

Для обычного монстра из актуального OS каталога при редактировании его мест появления в Энциклопедии появилась доступная из штатного ✎ замена **подтверждённой исходной** локации на другую. Клиент строит готовый список связей, проверяет существование заменяемого места и отправляет **один** `POST /api/admin/override` с ключом `spawnedit.<monsterId>`. Уже существующий `PandoraWikiOwnerData.apply` обновляет прямые и обратные индексы из одного снимка, не создавая временный промежуточный список без старой локации.

Для вручную созданных монстров, виртуальных карт и других нестандартных ссылок прежнее редактирование по одной связи сохраняется: оно может относиться к отдельным D1 ключам и не должно быть выдано за атомарную транзакцию. Никаких изменений исходного игрового каталога или схемы Worker.

## Завершение itemedit и отмены правок только после обновления Wiki (0.417.0)

После изменения предмета `saveWikiItemField` и отмены последнего изменения `undoOwnerEdit` дожидаются завершения `refreshOwnerCatalog()`. Состояние сохранения и блокировка повторной отмены больше не снимаются до реиндексации связей. Детерминированные Node-тесты используют задержанный Promise; публичная production D1 этим не изменяется. Эта правка не заменяет авторизованную проверку на живом сервере.
