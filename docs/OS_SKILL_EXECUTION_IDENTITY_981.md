# 0.981.0 — строгая идентичность цепочек навыков

## Исправленная ошибка

До обновления предпросмотр цепочек принимал любую существующую запись по `EP_SKILL_EXEC FV1[3]` при выполнении общих проверок направления и четырех коэффициентов. Замена дочернего ID на иной **существующий** навык могла создавать ложную цепочку, хотя реальный текущий каталог не содержал такой связи.

Теперь хранится независимый контракт идентичности **91 родительской записи и 99 ненулевых связей `EP_SKILL_EXEC`**. Для каждого родителя проверяется полный набор исходящих вызовов: число, порядок, конкретный ID, направление `TARGET`, `FV1=[0,0,0,childId]`, отдельный управляющий `FV2=[0,0,m,m]` с текущим значением `m=0` либо `9`. При несовпадении весь путь исключается из предпросмотра, а не перенаправляется на другой имеющийся навык.

**Два нулевых целевых ID** (`620002061`, `700000001`) остаются *пустыми целями*, а не ссылками на действие 0. В текущем каталоге значение `m=9` есть ровно у трёх связей, и обобщать его на другие действия нельзя.

## Исключения, которые нельзя ломать

Не все потомки имеют ту же ветку, нулевой список профессий или `learnable:false`. Зафиксированы настоящие случаи:

- `310023001 → 310023002`: конечная внутренняя запись помечена `learnable:true`, но не назначена профессиям.
- `410002001 → 500000005`: переход между двумя различными ветками.
- `430059001 → 230001002`: связанная групповая скрытность ведёт в другую ветку.
- `430058001 → 430058002 → 430058003 → (500000004 / 500000003)`: разветвление после двух промежуточных шагов.
- `440003001 → 440003002 / 440003003`: две дочерние ветви одного навыка.

Грубая проверка «потомок обязан быть той же ветки и всегда `learnable:false`» была бы неверна. Проверять нужно реальные связи и их изменения, а не придумывать универсальную схему.

## Доказанные и недоказанные свойства

Контракт подтверждает только **идентичность связи** и байтовые значения управляющих полей. Он **не подтверждает** количество попаданий, вероятность срабатывания, длительность, выбор цели, урон, эффективность сопротивлений, порядок округления или серверную обработку каждой внутренней записи.

У цепочек сохраняются `sourceOnly:true` и `verified:false`, не появляются `finalDamage`/`finalAmount`, состояние постоянных статов героя не меняется. Четыре независимые цепочки `EP_ONHIT_SKILL_EXEC` продолжают проверяться своим отдельным точным контрактом. При реальном изменении связей в следующей версии каталога необходимо обновлять контракт после независимого анализа, а не молча принимать чужой ID.
