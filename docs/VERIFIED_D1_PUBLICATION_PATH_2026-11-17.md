# Проверенный путь публикации production Cloudflare D1 через GitHub Actions

**Актуализировано:** 17 ноября 2026 года · Pandora Saga Build Studio

## Что реально подтверждено

У проекта существует защищённый путь записи в production Cloudflare D1 **без передачи личного пароля владельца в чат**: одноразовый GitHub Actions workflow, использующий настроенный GitHub secret `CLOUDFLARE_API_TOKEN`. Это проверено реальным [PR #692](https://github.com/bonaqu/Pandora-Saga-Build-Studio/pull/692) и [успешным запуском #44012837738](https://github.com/bonaqu/Pandora-Saga-Build-Studio/actions/runs/44012837738).

Из семи предметов (19010, 19011, 20027, 20028, 21019, 21020, 22022) были изменены **только уровни 55 → 50**. Запуск подтвердил точечную запись, сохранение 1 140 предметов, корректное переключение D1 snapshot посредством CAS и публичный readback. Далее все 16 игровых публичных наборов совпали с резервным источником, **0 blocking failures**. [Issue #683](https://github.com/bonaqu/Pandora-Saga-Build-Studio/issues/683) закрыта; [повторная браузерная приёмка](https://github.com/bonaqu/Pandora-Saga-Build-Studio/actions/runs/44013749610) показала нужные ограничения на 49-м и 50-м уровнях.

**Код для повторного изучения:** `scripts/publish-seven-item-levels-once.mjs`, `.github/workflows/publish-seven-item-levels-once.yml`, `tests/d1-seven-item-level-publication.test.mjs`. Ранее по схожей модели опубликованы шесть переводов подземелий через `scripts/publish-six-instance-ru-once.mjs`.

## Как действовать при следующем разрешённом обновлении

1. Проверить текущую ветку, новые PR, доступные workflow GitHub, права Actions и наличие настроенных секретов **по факту**, а не на основе старого ответа «доступа нет». Наличие секрета проверяется в CI без раскрытия значения. Если подходящего инструмента записи нет, установить причину и сообщить её.
2. Получить **явное одобрение владельца** на конкретный состав изменяемых данных. Не считать разрешение на предыдущие семь ID бессрочным согласием менять другие поля, аккаунты и билды.
3. Выполнить read-only preflight активного Worker/D1: источник `d1`, snapshot ID, точные цели и expected old/new значения, статус резервного источника, полный охват и отсутствие дополнительных расхождений. Если появились неизвестные изменения, остановиться.
4. Создать narrow, one-off GitHub Actions workflow с запуском только после reviewed merge или ручного `workflow_dispatch` с точным подтверждением. Связанные PR обязаны пройти Node и настоящий Chromium, а секреты недоступны PR-коду без объединения.
5. Авторизованно скопировать **действующий** D1 snapshot и все его наборы данных в staging. Не заменять весь каталог статическим резервным JSON: в D1 могут быть уникальные разметка, локализации и метаданные.
6. Изменить только заранее подтверждённые поля в staging с точными preconditions, проверить результаты каждого UPDATE, полный набор ID/количества, неизменность остальных записей и отсутствие потерь. Переключить `catalog_current` только через условную CAS-операцию по ожидаемому active snapshot. При конфликте — отказ, без перезаписи чужого обновления.
7. После успешной записи сверить authenticated D1 и **публичный Worker**, включая snapshot provenance. Проверить основные расчёты в Chromium, где это применимо, и `npm run catalog:parity:live` (16/16). Не заявлять успех только на основании успешно объединённого PR. Не проводить проверки внутри игрового клиента, если их нельзя выполнить.
8. Зафиксировать результаты и ссылки в соответствующей задаче GitHub. Если вместо успеха есть ошибка или CDN отдаёт предыдущий снимок, явно различать CAS-запись и подтверждение публичной доступности.

## Ограничения и безопасность

- Доступ через GitHub Actions **не является** универсальным прямым доступом к любым D1-данным. Действующие права токена, пределы Cloudflare, CI, CAS и валидация должны быть проверены для каждой операции.
- **Нельзя** читать или копировать значение `CLOUDFLARE_API_TOKEN`, вставлять секреты в PR, подделывать администраторские сессии, ослаблять защиту или менять аккаунты, библиотеку билдов и пользовательские данные, если они не входят в отдельно одобренный сценарий.
- Запись в локальный `data/os/*.json`, GitHub PR или GitHub Pages **сама по себе не публикует** D1. Потребуется отдельный защищённый процесс.
- Движок не должен выдумывать игровые эффекты, шансы, формулы или проверки, которые отсутствуют в источнике. «Совпали 16/16 датасетов» — это целостность каталога, не доказательство неизвестной игровой механики.
- Никаких периодических CI задач, cron-автозапусков или непроверенных массовых overwrite. Для конкретной задачи запуск должен быть явно ограничен.

**Практическое правило:** вместо категоричного «я не могу обновить D1» сначала проверить доступные GitHub Actions и Cloudflare workflow. Если безопасная запись подтверждена и одобрена, выполнить её и подтвердить readback. Если инструмент недоступен — прямо объяснить проверенное ограничение.
