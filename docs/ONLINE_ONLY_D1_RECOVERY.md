# Публичный онлайн-режим: Cloudflare D1 и сохранность билда

## Правило

Публичный Pandora Saga Build Studio открывает редактор только после успешной загрузки **согласованного снимка D1** и редакторских переопределений. Кнопка «Открыть архивную копию» отсутствует. Встроенные `data/os/` доступны только на `localhost` / `127.0.0.1` для разработки и независимого Chromium CI — не как запасной источник игрового каталога на опубликованном сайте.

`navigator.onLine` — вспомогательный сигнал, а не доказательство актуальности. Первичное подтверждение выполняется текущим строгим загрузчиком: девять каталогов с одинаковым `x-ps-catalog-snapshot`, заголовком `x-ps-catalog: d1`, проверками неполноты/структуры и обязательным чтением `/api/overrides`.

## Повторные обновления страницы и временные ошибки сети (0.882.0)

Для публичного сайта первоначальная D1-загрузка ограничивает количество одновременных запросов: три набора данных за раз вместо девяти; энциклопедия также запрашивает не более трёх. Только безопасные GET к опубликованному каталогу, переопределениям RU/EN и локальному файлу переводов повторяются при временных HTTP 408/429/500/502/503/504, таймауте или сетевом сбое (не более трёх попыток с короткими паузами). Для каждой попытки действует таймаут; общие ограничения запуска нельзя бесконечно продлевать.

**Не повторяются** POST, ошибки полномочий 401/403, отсутствующие записи 404, повреждённый JSON, отсутствие подтверждения `x-ps-catalog: d1`, различные D1 snapshot ID и ошибки целостности. Сайт не подменяет свежий каталог архивом. Если Worker действительно недоступен после ограниченных попыток, остаётся закрытый экран и уже существующее автоматическое восстановление через backoff без принудительного F5. История и текущий герой не стираются.

## Если первый запуск не удался

Экран остаётся поверх редактора и показывает только **«Повторить подключение»**. Ошибка не предлагает использовать устаревший каталог и не выдаёт подробности Worker/D1/API. При доступном соединении выполняются автоматические попытки с ограниченной частотой до успешной полной проверки. Вручную повторить попытку можно раньше.

## При подтверждённом D1, но нехватке места в браузере

После полной онлайн-проверки приложение должно отдельно подтвердить запись **обоих** локальных объектов: текущего героя и библиотеки билдов. Проверочная запись библиотеки не должна менять исходный порядок записей, если сами билды не изменились. Ошибка любого из этих сохранений **не разблокирует** редактор: состояние остаётся в оперативной памяти, виден экран «Не удалось сохранить изменения» и кнопка «Повторить сохранение». Повторная попытка касается только localStorage — не перезапускает D1-загрузку и не отправляет текущий черновик в облачную библиотеку. После успешной записи экран закрывается, сохраняется тот же герой, а авторизованная библиотека может повторно считаться из аккаунта.

## Во время открытого билда

Каждые 45 секунд при видимой странице, при возвращении фокуса и по событию возврата соединения проверяются **только чтением**:

1. `GET /api/catalog/meta.json` — успешный ответ, `x-ps-catalog: d1`, идентификатор снимка и обязательные счётчики.
2. `GET /api/overrides` — успешный ответ и объект авторских переопределений RU/EN.

Эти данные сопоставляются со снимком, первоначально принятым редактором. При сетевой ошибке интерфейс блокирует дальнейшее редактирование с прежними данными, **но не очищает** черновик, библиотеку, вкладки, авторизацию или формы. Перед блокировкой выполняется попытка сохранить владельческий текущий черновик и локальную библиотеку. Если локальное хранилище заполнено, сообщение прямо запрещает закрывать вкладку: сохранение не заявляется как успешное.

**Тот же снимок после восстановления:** блокирующий экран закрывается, открытый герой остаётся на месте; только после повторной проверки запускается существующая облачная синхронизация по учётной записи. Несохранённый текущий герой не отправляется в D1 автоматически. Если локальная запись не удалась, редактор продолжает показывать блокирующее предупреждение «Не удалось сохранить изменения» и кнопку «Повторить сохранение» даже после восстановления сети, пока повторная запись в браузер не станет успешной.

**Новый снимок или изменённые авторские тексты:** редактор остаётся заблокированным до явного «Сохранить и перезагрузить». Если у авторизованного редактора ещё открыт несохранённый текст, экран предлагает выделить и скопировать его, а затем отдельно подтвердить перезагрузку: автоматической D1-записи по потере фокуса не происходит. Рефреш сначала выполняет `pandora:before-update`, проверяет сохранность черновика и библиотеки и защищает незавершённые операции аккаунта/CAS. Старые игровые данные не подменяются посреди расчёта. Публикация игрового каталога через панель владельца тоже приводит к защищённому экрану обновления, а не к незаметной замене данных в открытом билде. Повторная загрузка снова требует всей строгой проверки D1. Обычное обновление версий UI продолжает обслуживать `pandora-studio-update-manager.js`.

Простой доступ к интернету не доказывает, что текущий D1 отражает последние правки **игрового сервера Pandora Saga OS**. Актуализация данных игры — отдельный процесс «Обновление игрового каталога».

## Проверка во время первоначальной загрузки

Каталог на публичном сайте загружается и проходит структурную проверку, но до заключительной сверки D1 и редакторских текстов нормализация старых очков навыков, экипировки и душ выполняется только **в памяти**. Если загрузка отклонена, исходный черновик восстанавливается; запись в браузер происходит только после подтверждения онлайн-снимка. Ручные повторы и автоматические попытки не запускаются параллельно, чтобы не смешать два набора данных.

## Защитные условия

- Не удалять сохранённые билды при неуспешном сетевом запросе.
- Не подменять ошибку облачной записи сообщением «сохранено».
- Не переходить к локальному архиву на публичном сайте.
- Не регистрировать Service Worker или тайный офлайн-кэш каталога.
- Не обновлять экран через перезагрузку в фоне и не стирать одноразовый код восстановления.
- Не писать в production D1 в проверках: тестовый API имитируется локальными ответами.
- Не разрешать отправку форм, клавиатурные действия и случайное сохранение owner-редактора по `blur` за блокирующим экраном.
- Пока экран подключения или безопасного обновления **фактически виден** (включая короткую анимацию закрытия и загрузку EN), все фоновые компоненты находятся в нативном `inert`, включая новые динамические кнопки; первоначальные `inert`-состояния восстанавливаются при скрытии диалога. Фокус находится внутри диалога, Retry доступен с клавиатуры, а прежний элемент получает фокус только после разблокировки.
- Не запускать загрузку облачной библиотеки аккаунта до подтверждения D1, а после восстановленного соединения сразу повторять чтение библиотеки без дополнительного PUT.
- После любого асинхронного ответа библиотеки (включая отложенный GET) повторно проверять актуальность онлайн-барьера **до** объединения записей и отправки PUT/DELETE. Прерванная синхронизация не уничтожает локальные копии.

## Проверка изменений

`npm test`, `npm run test:browser`, `npm run release:check`. Браузерные сценарии `online-d1-required-878` и `online-owner-draft-879` проверяют первоначальную недоступность, ручное подключение, сохранение героя, отказ при неуспешном повторе, восстановление той же версии, запрет незаметной подмены, явную перезагрузку на следующей версии и отсутствие записей в D1.

Владельцу не нужны эксперименты в реальном клиенте Pandora Saga. GitHub Actions проверяет код, а опубликованную Pages/Worker-D1-связку следует отдельно подтверждать на чтение после выкладки.

Аудит корректности online-only режима проводится в [Issue #723](https://github.com/bonaqu/Pandora-Saga-Build-Studio/issues/723); прежнее прохождение CI само по себе не заменяет проверки ситуаций, ранее не покрытых тестами.

## Менеджер обновлений (0.885.0)

Предложение новой версии не даёт права перезагрузить страницу во время восстановления D1 или до полного скрытия блокирующего экрана. Даже ручная кнопка «Обновить» проверяет незавершённые формы, модальные действия и режим владельца. Нажатие мышью не снимает фокус с редактируемого поля, если обновление пока запрещено, чтобы не вызывать неожиданное сохранение в D1 по blur. RU/EN сообщение объясняет действие для продолжения. Запросы проверки версии объединяются до полного чтения JSON, а сетевой таймаут не снимается после получения заголовков.

## Обновление после завершения режима владельца (0.898.0)

Токен владельца может сохраняться после кнопки «Завершить»/«Выключить редактирование», но наличие авторизованной сессии само по себе **не** означает активную правку и не должно блокировать «Обновить». Ручной и автоматический переход используют общую причину блокировки: D1-гейт, аккаунт, открытое поле/окно, активный owner-редактор или неоконченную CAS-очередь. После завершения редактирования сообщение в баннере обновления возвращается к обычному приглашению.

Операции выхода из редактора также защищены: открытое несохранённое поле, неподтверждённый результат D1 или незавершённая запись не исчезают без явного сохранения, отмены или устранения ошибки. Node-сценарии исполняют реальный guard приложения; production D1 для проверки не изменяется.

## Строгие свежие GET и отмена (0.893.0)

Общий загрузчик опубликованных игровых данных принудительно задаёт `cache: no-store` для всех read-only GET, независимо от вызывающего кода. Полученный после отмены запроса или истечения его таймаута ответ не считается пригодным снимком даже при сетевом адаптере, игнорирующем `AbortSignal`. Временные HTTP 429/503 с `Retry-After` учитывают только короткую задержку, ограниченную 2,5 секунды; некорректное значение оставляет прежний ограниченный backoff. Тесты добавлены в существующий `tests/live-d1-retry-882.test.mjs`. Никаких новых прав записи, архивного fallback или изменения игровой модели это не вводит.


## 18.11.2026 · 0.905.0 — защита общего загрузчика от архивного отката

`PandoraWikiCatalog.load` теперь отказывается использовать архив на публичном хосте даже при отсутствии `strict:true` у вызывающего кода; `preferLocal:true` блокируется до запроса. Узкий путь fallback на локальный набор сохранён исключительно для изолированных Node / localhost / 127.0.0.1 тестов, где `root.location` отсутствует или точно указывает на тестовый хост. `loadCatalog({archive:true})` в приложении также запрещён на публичном хосте. Старый HTML-баннер архивного режима удалён. При ошибке D1 публичный сайт остаётся на блокирующем экране и не заменяет каталог JSON из GitHub Pages.

## Диагностика недоступного production D1 после публикации (0.911.0)

Если `Live Pages and Worker readiness` завершился ошибкой, итоговая стадия автоматически запрашивает **только метаданные** той же базы `ps-build-studio-db` с зафиксированными Cloudflare account/database ID. Скрипт `worker/scripts/check-readonly-d1-incident.mjs` использует исключительно `SELECT`, `COUNT(*)` и `PRAGMA table_info`, проверяет идентификаторы перед выполнением и не выводит токены, логины, хэши, содержимое предметов или идентификаторы опубликованного снимка. Ошибки диагностики не маскируют исходный сбой релизной проверки. Дополнительного cron, фоновых опросов и записи в D1 нет.

Последовательность расследования по журналу GitHub Actions:

1. Сверить `Wait for expected public Pages version`: успешный Pages релиз сам по себе не доказывает готовность Worker/D1.
2. Сопоставить `D1 incident tables`, `active_catalog_rows`, `published_catalog_entry_rows`: отсутствующая таблица, пустой указатель и отсутствие строк у указанного снимка — разные неисправности.
3. Проверить `account_columns` и `session_columns` с исходными SQL-миграциями прежде, чем менять аккаунты или сессии. HTTP 500 от `/api/account/me` при тестовом токене не является доказательством повреждения пользовательских учётных записей.
4. Если удалённый SQL недоступен, не создавать каталог заново, не запускать миграции и не восстанавливать Time Travel по догадке. Сначала найти причину по Cloudflare D1 и проверить, что восстановление не затронет новые билды, аккаунты, переопределения и CAS-правки. Любое восстановление требует отдельной сверки и согласованного решения.

**Наблюдение 2026-11-19:** релиз 0.910.0 успешно прошёл Node/Chromium, GitHub Pages опубликовал его, но read-only контроль обнаружил каталог HTTP 503 и аккаунтный `/api/account/me` HTTP 500 (21 проваленная проверка); повторная проверка подтвердила ошибку. В 22:43 UTC предыдущий релиз 0.909.0 проходил ту же приёмку. Код Worker и production D1 не менялись в PR #762, поэтому причинность этого сбоя не установлена. См. [отчёт GitHub Actions](https://github.com/bonaqu/Pandora-Saga-Build-Studio/actions/runs/44418049849). Публичный онлайн-гейт продолжает блокировать устаревший каталог, не подменяя его архивом.

## 0.912.0 · D1 лимиты, аналитика чтений и экономия CI

Read-only расследование 0.911.0 показало: после ошибки каталога (HTTP 503) и аккаунта (HTTP 500) четыре `SELECT`-проверки (включая каталог) не завершились, при этом `PRAGMA table_info` для обеих аккаунтных таблиц вернул ожидаемые колонки. Это **не доказывает**, что записи каталога исчезли. До подтверждения исходной SQL-ошибки запрещено применять миграции, заново публиковать старый снимок или восстанавливать Time Travel.

Согласно [официальному объявлению Cloudflare](https://developers.cloudflare.com/changelog/post/2026-09-01-d1-free-tier-limit-enforcement/), с 1 сентября 2026 года Workers Free блокирует запросы после исчерпания суточного лимита чтений/записей D1 до 00:00 UTC, **не удаляя данные**. [Бюджет Free](https://developers.cloudflare.com/d1/platform/pricing/) — 5 млн прочитанных строк и 100 тыс. записанных строк в день. Это возможная, но пока неподтверждённая причина нашего инцидента.

При следующей неуспешной live-проверке диагностический скрипт отдельно классифицирует ответ о превышении **row-read** или **row-write** лимита, добавляет `SELECT 1` и запрашивает через [официальный Wrangler Insights](https://developers.cloudflare.com/d1/observability/find-expensive-queries/) самые затратные за сутки SQL-запросы. В журнал идут только категория запроса, число прочитанных/записанных строк и число выполнений; сам SQL, значения параметров, логины и хэши не выводятся. При отсутствии права `Account Analytics Read` отчёт пишет «insights unavailable», не маскирует исходный сбой и ничего не изменяет в базе.

Фильтры `workflow_run.branches` ограничивают автослияние каталога его собственными ветками, а восстановление оригинальных иконок — опубликованной веткой; это убирает десятки ненужных skipped-run при обычном CI, не выключая Node, Chromium или защиту от случайного merge. [Правило веток GitHub Actions](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#onworkflow_runbranchesbranches-ignore).

## 0.913.0 — меньше чтений D1 без потери актуальности

Публичные GET `/api/catalog/<dataset>.json` каждый раз **сначала читают** `catalog_current` в D1. При его недоступности ответ — HTTP 503, архивное или ранее кэшированное содержимое не выдаётся. Только после успешной проверки указателя Worker использует локальный кэш Cloudflare Cache API по ключу `snapshot + dataset` с TTL 3600 секунд (один час, поскольку опубликованные снимки неизменяемы). Для **всех внешних HTTP-ответов**, даже при попадании в Cache API, Worker устанавливает `Cache-Control: no-store`; иначе Cloudflare Workers Cache способен отдать ответ ещё до запуска Worker и пропустить обязательный запрос текущего указателя. `Cache-Control: public, max-age=60` устанавливается **исключительно на отдельной копии ответа** внутри Cache API. Кэшированная запись обязана иметь точные заголовки `x-ps-catalog: d1` и `x-ps-catalog-snapshot`. После публикации нового снимка ключ другой. Изоляция Cache API по датацентрам означает, что число фактических промахов зависит от географии запросов и нагрузки, поэтому экономию строк D1 нужно оценивать по метрикам, а не обещать фиксированный процент.

Админский batch API отвергает попытки перезаписи уже опубликованной версии. Атомарный SQL-запрет повторяется внутри `INSERT ... SELECT ... WHERE NOT EXISTS ... ON CONFLICT ... WHERE NOT EXISTS`, чтобы конкурентная публикация между проверкой и записью не нарушала неизменяемость снимка. При обнаружении гонки ответ 409; администратор должен подготовить новую версию, а не менять опубликованную. **Никаких фоновых D1-записей, миграций или новых cron.**

После merge исходного кода автоматический Worker deploy выполняется отдельно от GitHub Pages. Только успешная проверка `catalogSnapshotCache: true` в живом `/api/runtime-capabilities`, D1 provenance и всех 16 наборов подтверждает доступность оптимизации на production. Обычный номер версии HTML недостаточен.


Ограничение платформы и механизм двух разных кэшей подтверждены [Cloudflare Cache API](https://developers.cloudflare.com/workers/runtime-apis/cache/) и [Workers Cache](https://developers.cloudflare.com/workers/cache/). Кэш не является источником истины, он только сокращает повторное чтение уже подтверждённого снимка.
